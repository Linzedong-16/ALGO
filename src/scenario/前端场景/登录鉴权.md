## 常用的登录鉴权方式以及优缺点

1. Session-Cookie：Session是服务端存储的用于记录用户会话标识用户身份的记录，一般通过内存或Redis(常见)实现，SessionID被携带到下发给客户端的Cookie中，之后的请求自动携带cookie，并通过在Session中查标识用户的SessionID完成鉴权。
   优点是：数据放在后端，更安全、强可控随时销毁会话
   缺点是：对于分布式系统不友好，因为多次请求可能会被分发到不太的服务机，这样又涉及到了Session数据共享、粘性会话(标记服务机)的问题，然后对于非浏览器环境不适用

2. Token：服务器生成一份令牌给客户端，之后客户端每次请求在header中携带令牌发送到服务器，后端通过验证令牌的时效与签名放行请求。最常见的形式是JWT：通过base64编码的三段字符串：header(算法+令牌类型).payload(业务字段+过期时间、签发信息的标准字段).signature(防篡改的加密字符串)。
   优点：对分布式友好，非浏览器环境也适配
   缺点：token不可控，需要黑名单机制或AT+RT双Token机制尽量避免安全问题

3. OAuth2.0：这是一个授权协议，一般用于授权第三方用户访问其他平台的资源，对第三方的依赖高，如微信、Github、Google等知名的第三方可以很方便登录其他绝大部分平台

4. API Key：内部微服务调用、第三方开发平台调用，如在deepseek开放平台，申请API key后，可以配置Claude code或其他AI客户端就可以使用，不用于常见的C端场景，因为API-Key一旦泄露只能向平台申请销毁

### JWT签发后怎么失效

1. JWT本身无状态，可以通过维护黑名单不放行某些携带Token的请求
2. 双Token机制：AT过期时间可以缩短，用RT再续期，RT可以通过轮转刷新+黑名单尽可能避免 Token劫持等风险
3. 加入version机制，还可以实现批量用户快速踢下线等的操作
   > 搭配使用更佳

### Session 分布式场景解决方案

1. Session复制，多台机子同步Session，最差方案
2. 粘性会话，就是让Nginx 通过设置标记把同一个用户的请求匹配转发到同一个机器
3. Session外置，最佳方案是将所有会话抽离出一个中间件，如Redis去集中管理 Session，所有机器共享
